## 2026-09-12 · 第 2 轮

**D-009** · 新项目不受现有项目束缚。`docs/product/` 只是借本仓库存放讨论记录；技术选型、架构、代码全部以讨论结论和实际需要为准，不默认延续 Next.js / Vercel / 现有代码。
> Kai Li 特别强调，需在每次会话开始时重申。

**D-010** · 收集资源时提供输入框，顺手记下「当时的想法」。这是资源库区别于书签工具的核心机制。
> 不做「强制」，而是「顺手」：把输入框放在保存流程里最显眼的位置，不填也能保存。

**D-011** · 文章可以「源自」某条资源：一段时间后觉得值得深想，就基于该资源和当初的想法扩写成文章。文章不必深，**写了就是给自己一个深入想的机会**。数据上资源与文章之间要有可追溯的来源关系。

**D-012** · 文章只有一种类型，不区分 essay / note。短想法不作为独立的公开内容类型，而是作为资源上的评论（即 D-010 的输入框）存在。
> Kai Li 的理由：短评不如直接发 X；个人站短期内不会有多少人看。
> 遗留问题：资源评论是否有公开视图 → todo P1。

**D-013** · 「脉络」= 手工记录的业界重点事件时间线，不是从文章 / 资源聚合出来的。supersedes requirements §5 第 1 轮的方向 a/b/c 框架。
> 举例：2026-09 初国内中转站被曝蒸馏用户与模型的对话、部分模型把请求路由到国外模型（国内大模型发展的节点）；DHH 发布新的 Linux 发行版。凡是有影响力的事件都值得记一条。

**D-014** · 资源库优先级高。开发顺序：先博客，但**博客的设计必须从第一天就为资源库留位置**；博客完成后立刻开始资源收集器的核心 / 基础功能，边做边打磨。

**D-015** · 双语策略：同一篇文章提供中英两个版本；站点从首页开始按浏览器语言自动展示对应语言；首页列表**不再用 EN / 中 徽标**。supersedes D-008。
> 细节（是否每篇都必须双语、AI 翻译、URL、手动切换）→ todo P0。

**D-016** · 分类 + 标签都要。分类是单选栏目，标签多选；分类实现不复杂，且方便检索。

**D-017** · 不做评论功能。每篇发布后在 X 发一条推文，讨论在 X 上发生。后期如有需要再加。

## 2026-09-12 · 第 3 轮

**D-018** · 每篇文章**必须**有中英两个版本，不允许单语发布。
> 理由：双语写作本身是 Kai Li 学英语的手段，不是纯粹的读者服务。

**D-019** · 英文版由 Kai Li 自己写，AI 负责改进（润色 / 纠错），不是 AI 翻译。
> 产品含义：编辑器需要「AI 改进英文」能力，且要能看到**改了什么**（diff 视图），否则学习效果为零。这个能力是第一版编辑器的一部分，不是后话。

**D-020** · 编辑器不做中英并排；两个语言版本以切换（tab）方式编辑。

**D-021** · 发推联动不用 AI 生成推文内容。推文由 Kai Li 手写；系统最多只做「预填链接 + 一键打开 X 编辑框」这种零内容的辅助。
> 理由：AI 味的推文会让人第一眼就不想点。

**D-022** · 脉络公开。

## 2026-10-02 · 第 4 轮

**D-023** · 首期技术架构：采用 TanStack Start + React，部署到 Cloudflare Workers，整体保持模块化单体。公开文章页使用运行时 SSR 返回完整 HTML；不把 SSG 和发布构建流水线作为首期要求，公开页通过缓存获得接近静态的访问特征。
> 理由：对照验证中，TanStack Start 以较少的自建边界同时满足了公开文章 HTML、动态 metadata、API 和 Cron；Cloudflare 提供了官方部署路径和 AI Coding 所需的平台文档 / MCP 上下文。TanStack Start 仍处于 Release Candidate 阶段，但 Kai Li 接受这一风险，并愿意使用 AI Coding 作为主要开发方式。
> 范围：公开站、后台、API 和定时任务共享一个项目与领域模型；数据库、单用户鉴权、对象存储、全文检索和 Cron / Queue / Workflow 的具体组合仍未决定。

**D-024** · 首期结构化数据使用 Cloudflare D1；图片、网页快照和其他大对象使用 R2。D1 满足当前单用户、低写入、关系型内容系统的需求；数据库访问通过独立的数据访问边界组织，避免把 D1/SQLite 细节散落到领域逻辑中。
> 理由：现有文章、资源、标签、来源关系和事件模型可由 SQLite 表、外键、索引和事务性 batch 表达。D1 与 Workers 的内部访问路径更简单，避免增加 Worker 到外部 PostgreSQL 的网络链路；但不承诺中国大陆实际延迟一定更低。
> 可迁移约束：采用标准关系模型与可同时支持 SQLite / PostgreSQL 的查询工具；D1 专属 SQL 和 FTS5 不作为领域层契约。迁移 PostgreSQL 时，允许重建索引、迁移脚本和数据访问适配器，不要求零成本迁移。
> 仍未决定：全文检索具体方案、中文搜索体验、R2 bucket 公开访问策略、单用户鉴权、后台任务组合。

**D-025** · 澄清 D-024 范围：本轮确认的是 D1，R2、全文检索与 ORM / 查询工具仍为候选；supersedes D-024 中把 R2 和跨数据库查询工具写成已定的部分。
> PostgreSQL 迁移约束：SQL 与 D1 binding 集中在服务端数据访问模块；不提前实现第二数据库适配器。迁移时需要转换 SQLite schema、数据类型、查询、事务调用及全文索引，不承诺改连接字符串即可迁移。
> 官方证据：D1 可导出 SQLite SQL，但当前内置导出不支持含 FTS5 虚拟表的数据库；搜索索引应可由原始内容重建。来源：https://developers.cloudflare.com/d1/best-practices/import-export-data/
> 成本判断：当前小型内容系统没有必须使用 PostgreSQL 的功能性理由，但完整迁移尚未演练，不能承诺固定工期。以后迁移出 Cloudflare 时，Worker 入口、Cron / Workflow 和文件存储的替换是独立成本。

## 2026-10-03 · 第 5 轮

**D-026** · zh / en 是两个独立的内容版本，可以分别保存、分别发布；一篇文章可以只有一个已发布语言版本。某语言版本未发布时，该语言的首页、列表和文章页不显示它。supersedes D-018 关于“两个版本齐全后才能发布”的约束。
> 文章数据模型仍保留两个语言版本；这里改变的是发布前提，不是取消双语字段。

**D-027** · 访问者首次访问时按浏览器语言自动选择应用语言；顶栏在 light/dark 模式旁提供语言切换按钮，手动选择覆盖自动选择并记住选择。语言切换作用于当前页面，包括当前文章的语言版本。未发布的语言前缀 URL 返回 404；语言中立分享链接优先选择浏览器语言对应的已发布版本，缺失时回退到另一已发布版本，两种都未发布时返回 404。

**D-028** · AI 改进英文不是无参数的一键覆盖：Kai Li 可以提供本次修改指令，AI 返回 diff 提案；Kai Li 逐处接受或拒绝，未接受的提案不写回正文；对不满意的结果可以带新指令再次生成提案。

**D-029** · 已发布的语言版本继续编辑时，保存后立即更新该语言的公开页面；另一语言版本不受影响。发布后的修改暂不创建第二个待发布版本。

**D-030** · 首期英文版本可选：Kai Li 可以自行写英文，也可以基于中文生成 AI 英文草稿，再人工检查、修改并独立发布。AI 不自动发布；中文发布不等待英文。supersedes D-019 中“英文只能由 Kai Li 自己写、不能由 AI 翻译”的限制，以及 D-028 将复杂 diff / 逐处接受拒绝 / 多轮修改交互作为首期必需的部分。
> 理由：首期优先保持写作和发布简单，同时保留自行写英文练习输出的选择。AI 翻译草稿和 AI 改进自写英文是不同能力；复杂英文改进交互后置，是否需要由实际使用决定。
> 范围：保持 D-026 的按语言独立保存和发布，以及 D-034 的保存不公开、发布才更新线上规则。中英文不要求逐句同步；重新生成英文时如何处理已有英文内容仍待讨论。

**D-031** · `tweetUrl` 与文章页「在 X 上讨论 →」链接不进入首期。文章可以正常发布，不要求保存对应 X 帖子链接；未来若确实需要把讨论导向文章专属 X 帖子，再单独加入。
> 理由：个人博客预期阅读量有限，讨论更可能直接发生在 X；保存链接增加后台维护步骤，但不影响文章核心发布流程。

**D-032** · 首期使用现成的、轻量的 Markdown 编辑器并提供预览；不自研编辑器，不使用块编辑器。具体编辑器库、预览布局、图片粘贴和快捷键另行讨论。

**D-033** · D-017 中“不做评论区”继续有效；文末放对应 X 帖子链接的部分不进入首期，按 D-031 后置。supersedes D-017 的首期 X 链接要求，不推翻“不做评论区”。

**D-034** · 保存只保存当前语言版本的编辑内容，不改变公开页面；发布才把该语言版本更新到公开页面。编辑已发布版本时，保存后的内容仍是待发布编辑内容；再次发布后才公开。只保留当前草稿和当前公开内容，不做历史版本、审核流或回滚界面。supersedes D-029。
> 理由：个人站不需要复杂 CMS；保存与发布分开可以避免未完成的修改立即公开，同时只增加当前公开内容与当前编辑内容两份状态，不引入历史版本系统。

**D-035** · 允许根据中文重新生成英文。新译文先展示，不自动覆盖已有英文；Kai Li 确认后才替换当前英文编辑稿，可以继续手动修改。已有英文已发布时，公开内容保持不变，仍需按 D-034 再次发布才对外生效。不做逐句 diff、多份候选稿或翻译历史；明确 D-030 中已有英文时重新生成的待议行为。

**D-036** · 顶部主题切换旁的语言按钮切换整个应用，始终可用。当前文章有已发布的目标语言版本时进入对应文章页；目标语言缺失或未发布时进入目标语言文章列表，并仅在本次切换后提示一次。英文提示为「This article isn't available in English.」，中文提示为「这篇文章暂无中文版」。普通进入列表页不显示该提示。
> 澄清 D-027 的全站语言切换行为，替代此前需求正文中「只显示当前文章已发布语言入口」的限制。直接访问未发布语言文章 URL 仍返回 404；中立分享链接的回退规则不变。

**D-037** · 首期后台提供一个分类与标签管理页面，使用两个 tab 分别管理。文章分类单选、标签多选，沿用 D-016。读者在统一文章列表通过 URL query string 筛选，不创建独立公开分类页或标签页。
> 筛选规则：首期读者一次选择一个分类、一个标签，同时选择时取交集；只返回当前语言已发布内容。筛选状态可通过 URL 保留、刷新和分享，例如 `/zh/writing?category=engineering&tag=typescript`。
> 理由：沿用 Kai Li 之前的博客经验，满足内容维护和查询，不增加专题页；避免 `/writing/<category>` 与 `/writing/<slug>` 的路径冲突。具体管理页及筛选控件界面另行讨论。

**D-038** · 文章编辑采用手动保存，不做首期自动保存；保存只写入当前语言版本的编辑内容，不改变公开页面，发布才更新线上。页面离开前可提示存在未保存修改，但不引入服务端自动保存。
> 理由：这是单用户个人写作工具，不需要多人协作或在线文档级的持续保存；手动保存能保持“保存”和“发布”的边界清楚，避免首期增加自动保存状态和失败处理。

**D-039** · 首期草稿只在编辑器内预览，不生成独立草稿预览链接；未发布内容不提供给公开页面、搜索引擎或未登录用户访问。
> 理由：单人写作不需要分享草稿或协作审阅；编辑器内预览已足够检查 Markdown 渲染效果，避免新增预览权限和路由。

**D-040** · 首期只支持手动发布，不做定时发布；不增加 `scheduledAt`、定时状态或 Cron 发布任务。
> 理由：个人文章发布频率低，定时发布不会改善核心写作流程，却会增加时间、时区、取消和失败处理。

**D-041** · 文章与资源采用可选的多对多关联：一篇文章可以关联零到多条资源，一条资源可以被多篇文章关联。从资源详情页发起写作时预选当前资源，文章仍可继续添加其他资源。资源删除时只删除关联记录，文章正文和已发布内容保留，不保留删除后的来源快照。D-041 supersedes D-011 中“文章源自单条资源”的关系模型，但保留从资源发起写作的入口。
> 理由：资源是灵感输入，文章是独立输出；单条来源无法表达多条灵感共同形成一篇文章，也不应让资源生命周期约束文章生命周期。

**D-042** · 第一版提供独立的私有 Idea 快速记录，用于保存没有外部来源的闪念。Idea 不是 Resource，也不是文章草稿；第一版只做快速记录、查看列表和转为文章草稿，转换后保留原 Idea。Idea、Resource、Post 相互解耦，具体字段和状态模型另行确认。D-042 同时确认资源获取入口暂时只保留 Chrome 插件，后台不提供手动新建资源的 URL 入口。
> 理由：无 URL 的内部想法不应伪装成外部资源；直接创建文章草稿又会提前引入标题、语言版本和发布状态。独立 Idea 能接住闪念，同时保持资源采集、想法记录和文章输出的语义边界。
> 修订：D-042 supersedes D-003 中关于“站内 Markdown 编辑”作为资源入口的表述，保留 Chrome 插件获取资源的部分；D-042 原先关于“Idea 可选关联资源”的表述已由 D-043 supersede。

**D-043** · 第一版不建立 Idea 与 Resource 的持久关联。Idea 转为文章草稿时只带入 Idea 文本；文章之后通过独立的 PostResource 关联零到多条资源。Idea 与文章的资源关联不自动同步。
> 理由：当前没有已确认的流程需要保存 Idea 的资源上下文；在文章编辑阶段关联资源已覆盖写作需要，新增 IdeaResource 会提前引入关系、复制和删除语义。
> 修订：D-042 / requirements §3.5 中“可选关联资源”的表述改为本决策；D-010 对 Resource.thought 的规则继续有效。D-044 已明确 D-012 中资源评论与 Idea 的边界，D-012 关于文章只有一种类型继续有效。

**D-044** · `Resource.thought` 与 `Idea.text` 是两种不同的短文本：前者是针对已保存外部资源的评论，后者是没有外部来源的独立闪念。D-012 关于文章只有一种类型继续有效；D-044 supersedes D-012 中把所有短想法都定义为资源评论的部分。无外部来源的短想法不要求挂在资源上，也不改变文章类型模型。
> 理由：文本长度相似不代表业务语义相同。资源评论依附于外部资源，Idea 是独立的私有输入；混用会让资源库无法区分外部输入和个人原创想法。

**D-045** · 第一版文章编辑器采用轻量、成熟的 Markdown 编辑方案：支持编辑、预览、手动保存、手动发布、中文/英文 tab 和基本 Markdown 渲染；具体编辑器库、布局与快捷键先按实现建议落地，使用中不合适再调整，不引入块编辑器或复杂协作能力。
> 理由：文章内容以文字和代码为主，Markdown 能满足当前需求；先验证写作流程，比提前锁定复杂编辑器细节更重要。

**D-046** · 文章中粘贴或选择的图片先上传到 Cloudflare R2；草稿图片默认不可公开读取，只有被已发布文章引用时才允许公开访问。上传对象先作为临时对象管理；文章保存时登记图片引用，已保存草稿或已发布文章引用的图片不得被清理。未被任何草稿或已发布文章引用的临时对象，才进入定期或按访问触发的 TTL 清理流程，清理时机和具体实现另行确定。
> 理由：R2 适合存储图片等对象；上传与公开读取分离，避免未发布内容因图片 URL 泄露而公开。浏览器崩溃、断网或页面关闭都不能可靠通知服务端立即删除，因此必须记录对象的引用状态，不能只依赖文件名判断是否可清理。

**D-047** · 未被任何草稿或已发布版本引用的临时图片，默认保留 7 天后才进入清理；清理执行前必须重新检查四类引用：`zh` 草稿、`zh` 已发布、`en` 草稿、`en` 已发布。只要仍有任一引用就不得清理；删除全部引用后，图片才按临时对象的 7 天宽限期处理。清理不使用 R2 bucket 生命周期无条件执行。
> 验收：用可控时钟验证上传后未保存的图片在 7 天内不能清理；删除全部引用后，超过 7 天才允许清理；清理前重新登记任一语言草稿或已发布版本引用的图片不能被删除。已保存草稿引用的图片不是永久保留，删除全部引用后仍按上述规则处理。

**D-048** · 图片引用按 `zh` 草稿、`zh` 已发布、`en` 草稿、`en` 已发布四个槽位独立登记；保存或发布只更新当前语言对应的槽位。R2 对象保持私有，登录后台可以读取草稿和临时图片，匿名访问只允许读取已发布版本引用的图片。
> 验收：修改中文草稿不能清除中文已发布或英文版本仍引用的图片；未登录访问草稿图片失败，登录后台预览成功；发布某语言版本后，该语言已发布引用的图片可公开读取。

**D-049** · 第一版文章页包含 TOC、阅读时长、上一篇和下一篇；上一篇/下一篇只在存在对应文章时显示。D-017 的评论区不做决定继续有效。
> 理由：这些元素能改善长文章阅读和文章间导航，但不引入评论、相关文章推荐等额外系统。

**D-050** · 第一版文章列表按发布时间倒序，显示日期、标题和摘要；沿用 D-037 的分类/标签筛选。首期不做分页和按年份分组，置顶沿用已有常规字段，不新增复杂排序规则。
