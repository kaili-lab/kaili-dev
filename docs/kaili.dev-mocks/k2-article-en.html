Moving Say Right from Next.js to Cloudflare Workers

Cold starts, KV consistency, the Durable Object bill, and the $19 a month it saved.

Say Right ran on Vercel for its first year. Traffic is small, but every practice session calls a model and writes a review record, and between cold starts and database connections the first request often took over two seconds. In August I moved the whole thing to Cloudflare Workers. These are the parts that actually took time.

Why move

Two reasons: latency and the bill. Most Say Right users are in Asia, while the functions and the database lived in US East. One practice session meant three round trips, and the network alone was half the wait.

Switching platforms was never the goal. If latency had been the only problem, moving regions would have been enough. What pushed me was the line item billed by execution time: it grew with every practice session, and most of that time was spent waiting for the model.

Cold starts were a non-issue

Cold starts worried me most and turned out to matter least. Workers run in V8 isolates rather than containers, so the first request looks like every other one. What did need changing was code that assumed a long-lived process, such as opening a database connection at module scope:

// Before: connect once at module load and hope the process stays alive
const db = new Pool({ connectionString: process.env.DATABASE_URL });

// After: take the binding per request, keep no global state
export default {
  async fetch(req, env) {
    const row = await env.DB.prepare("SELECT * FROM cards WHERE id = ?").bind(id).first();
    return Response.json(row);
  },
};

The change is mechanical, but you have to find every instance. grep -rn "process.env" listed about forty places; it took an afternoon.

KV consistency was the real trap

The Workers KV docs are clear: after a write, other locations may take a while to see the new value. I had read that sentence. I hadn't worked out where it would bite.

The minute of stale reads

I kept “today's review queue” in KV. Finish a card and the queue updates; refresh right away and sometimes the card you just practised came back.

KV is eventually consistent. Changes may take up to 60 seconds or more to be visible in other global network locations.

KV wasn't the problem. I had put something that must read its own writes into a store that doesn't promise that.

Switching to a Durable Object

One Durable Object per user, with the queue inside it. Requests from the same user always reach the same object, so reads and writes are consistent by construction. The cost is learning how it bills, which the next section adds up.

The bill

One month before and after the move, with roughly the same users and practice sessions:

ItemVercel + hosted DBCloudflare
Compute$20.00$5.00
Database$7.00$0.00
Durable Objects—$3.10
Total$27.00$8.10

About $19 a month saved. Not much, but it no longer grows with practice sessions, and that matters more than the number.

After the move

  1. The first request dropped from over two seconds to around 300 ms.
  2. No more reports of “the card I just did came back”.
  3. Local development moved to wrangler dev, which starts faster.

If your app has little traffic but waits on an external service for every request, a platform that bills by execution time makes you pay for the waiting. That is the one thing I wish I had known earlier.
