## 2. 用户要求

### U-01 · 使用 API key 接入

AI 服务以 API key 为主要接入方式，不依赖某个桌面应用或订阅制模型账号。

**要解决的问题**：应用部署在 Cloudflare Worker 后，仍能由服务端独立调用模型；不把 AI 能力绑定到个人电脑、IDE 或某一次人工操作。

**暂不裁决**：是否同时支持 OAuth / 订阅账号；第一版是否只支持 OpenAI-compatible API。

### U-02 · 允许配置多个接入

后台可以配置多个 AI 服务接入。当一个接入不可用时，应用可以按既定策略使用其他接入，避免单一供应商故障导致所有 AI 功能停止。

**要解决的问题**：单个供应商故障、限流、API key 失效或模型下线时，应用仍有降级路径。

**约束**：切换只能在允许接收该类数据的连接之间进行（见 S-04）。

### U-03 · 根据 baseURL 查询模型

填写 baseURL 和 API key 后，后台最好可以查询该提供方的模型列表，并形成可选择的模型列表。

**要解决的问题**：减少手动输入模型 ID 的错误，让管理员知道某个接入当前实际可用哪些模型。

### U-04 · 默认模型与显式模型选择

系统可以设置默认模型。具体功能通常直接使用默认模型，也可以在需要时显式选择其他模型。

**要解决的问题**：日常使用不需要每次选择模型，同时保留对特殊任务、测试模型或更便宜模型的控制能力。

### U-05 · 接入层服务于具体场景

当前已知的具体场景包括语义 slug 候选和点击按钮生成文章摘要。接入层的目的是让各场景共用供应商选择、错误处理和密钥读取，而不是每个按钮各自实现；但按 D-090，接入层与第一个场景一起建设，不先于场景单独完成。

## 3. 推荐的接入层形态

### 3.1 连接与模型分开

建议把“供应商连接”和“模型”设计成两个对象（拟替代 D-087 的单条配置结构，见第 0 节）。

```text
ProviderConnection
- name
- baseURL
- API key（存储方式见 S-01）
- enabled
- priority
- allowed data classes（见 S-04）
- last test result / time

Model
- connectionId
- provider model ID
- display name
- capability flags（管理员手动勾选）
- enabled
```

**解决的问题**：一个接入可以提供多个模型；同一个模型 ID 也可能出现在不同接入；停用一个连接时，不必把模型概念和连接配置混成一团。

### 3.2 按优先级依次尝试，不随机、不记冷却

多个连接按优先级选择，而不是随机选择。每次调用独立按优先级依次尝试，不在请求之间保存冷却状态。

```text
按优先级取第一个：已启用、允许接收本次数据类别、有满足能力的模型的连接
失败（超时 / 限流 / 服务错误）→ 尝试下一个合格连接
没有合格连接，或全部失败，或达到总时限 → 返回明确失败
```

**为什么不记冷却**：Worker 在请求之间不保留内存状态，冷却时间必须写入 D1 或 KV；个人网站调用频率很低，记录冷却带来的收益不足以抵消额外状态。

**总时限**：每个场景规定一次调用的总等待上限（含所有切换），由场景任务卡给出具体秒数。

错误处理：

| 错误 | 处理 |
|---|---|
| 网络超时 | 不在同一连接上重试，直接尝试下一个合格连接（超时请求可能已计费） |
| 连接拒绝 | 尝试下一个合格连接 |
| 429 限流 | 尝试下一个合格连接 |
| 500 / 503 | 尝试下一个合格连接 |
| API key 无效 | 尝试下一个合格连接，并在后台提示管理员该连接 key 无效 |
| 模型不存在 | 尝试下一个合格连接，并在后台提示管理员停用或修正该模型 |
| 请求不符合模型能力（调用前检查：所选模型未勾选所需能力） | 返回配置错误，不用其他供应商掩盖错误 |
| 返回格式错误（返回非 JSON，或 JSON 不符合场景规定的结构） | 不切换、不重试，直接返回结构化错误；后台提示管理员核对该模型的 `structured-output` 标签 |

### 3.3 模型发现必须允许手动填写

查询模型列表优先尝试 OpenAI-compatible 服务的 `/models`，但不能假定所有提供方都支持它。

后台应同时提供：

- 查询模型（只生成模型 ID 列表）；
- 手动填写模型 ID；
- 查看最近一次查询时间和失败原因；
- 停用无法使用的模型。

**解决的问题**：自定义网关、权限受限的 key 或非标准提供方可能不能列出模型，但仍然可以直接调用已知模型 ID。

### 3.4 模型需要能力标签

模型不能只存一个字符串，还应记录支持的能力。OpenAI-compatible 的 `/models` 只返回模型 ID，不返回能力信息，因此能力标签由管理员手动勾选。

第一阶段只需要：

```text
chat
structured-output   在 chat 基础上能按指定 JSON 结构返回；只能和 chat 一起勾选，要求 structured-output 即同时要求 chat
```

其他能力（embedding、vision、image-generation 等）在对应场景出现时再加；数据结构保留“一个模型有多个能力标签”的形式，不把所有模型假定为同一种能力。

**解决的问题**：不支持结构化输出的模型不会被要求返回严格 JSON；未来增加向量或视觉任务时不必重写模型选择逻辑。

### 3.5 默认模型按能力设置

每种**已有场景使用的能力**设一个默认模型；第一阶段只有一个（slug 候选所需能力的默认模型）。不设“全局默认模型”。

功能调用时的选择顺序：

```text
功能显式指定的模型
→ 该能力的默认模型
→ 按优先级的合格连接中、具备该能力的已启用模型
```

每一步都按同一组条件过滤：模型已启用且具备所需能力，所属连接已启用且允许本次全部数据类别（S-04）。显式指定的模型也不例外：不满足条件时返回配置错误，不调用。不存在“不区分能力的兜底模型”，避免把 embedding 或图片模型误用于文本任务。

## 4. 安全与可靠性要求

这些不是用户逐字提出的内容，是为了让 U-01 到 U-05 能安全落地而补充的约束。

### S-01 · API key 不明文存储、不外泄

API key 不应明文存入 D1，也不应出现在日志、错误信息、页面 HTML 或客户端脚本中。

后台应至少支持：

- 只显示脱敏后的 key；
- 新增、替换、删除 key；
- 验证 key 是否可用；
- 不允许读取旧 key 的完整值。

**待裁决**：两种存储方案。

| 方案 | 做法 | 能防什么 | 代价 |
|---|---|---|---|
| A · 主密钥加密存 D1 | 主密钥放 Cloudflare Secret，key 加密后存 D1 | D1 导出、备份泄露 | 主密钥和密文由同一个 Worker 读取，防不了 Worker 代码或后台被攻破；需要设计主密钥轮换 |
| B · 每个 key 一个 Wrangler secret | 后台只填 baseURL 和 secret 名 | D1 中不存任何 key | 新增或更换 key 必须执行 `wrangler secret put`，不能在后台完成 |

连接只有 2–3 个且很少换 key 时 B 更简单；需要经常在后台换 key 时选 A。**D-185 选 A**：Cloudflare secret 写入后无法导出，B 在迁出平台时要逐个重新录入；A 只需导出数据库并设置一个主密钥。

### S-02 · baseURL 请求的最低限制

baseURL 由管理员配置，请求从 Worker 服务端发出。后台只有 Kai Li 一人可进入，主要风险是 key 被发到错误地址。必须满足：

- 只允许 HTTPS；
- 设置超时；
- 不跟随重定向，收到重定向视为该连接失败（请求正文可能含草稿，只去掉 API key 不能阻止正文发到重定向目标）；
- 错误响应不得原样泄露 key 或请求头。

**暂缓**：内网地址、保留 IP、端口黑名单。Cloudflare 文档中未找到 Worker `fetch` 访问私有 IP / localhost 时的明确行为说明（未核实）；实施前先实测，再决定是否需要。

### S-03 · AI 失败不能破坏内容工作流

任何 AI 调用失败都必须满足：

- 不覆盖已有文章、Idea 或 slug；
- 不改变保存 / 发布状态；
- 不自动发布；
- 不阻止用户手动完成工作；
- 显示可理解的失败原因；
- 遵守场景规定的总时限。

**解决的问题**：AI 是外部依赖，不能成为保存文章或发布文章的单点故障。

### S-04 · 数据发送边界由连接级白名单执行

数据分类（候选，待裁决）：

```text
public    已发布文章的公开内容
draft     文章草稿（含标题）
idea      Idea
resource  Resource 正文和 thought
image     私有图片
```

管理员账号信息不属于任何类别，任何场景都不发送。

规则：

- 每个连接配置 `allowed data classes`；新连接默认只允许 `public`。
- 每个场景声明本次调用包含哪些数据类别。
- 接入层只在**允许全部这些类别**的连接之间选择和切换（3.2）；没有合格连接时直接失败，不降级到不合格的连接。
- 每个场景任务卡写明：发送哪些数据、是否需要用户确认。连接的配置界面提示管理员确认该供应商是否保存请求内容后，再勾选非 `public` 类别。

**解决的问题**：自动切换不会在无人确认时把私人草稿发给保存请求内容的供应商；数据边界由接入层执行，而不只是一条原则。

### S-05 · 调用记录

接入层每次调用记录：

- 时间；
- 连接和模型；
- 功能用途；
- 成功 / 失败及错误类别；
- 延迟；
- 是否发生切换；
- 输入 / 输出 token（供应商提供时）。

不保存完整 prompt 和完整返回内容，因为其中可能包含私有草稿。

**暂缓**：每日 / 每月预算、日志保留期限、删除调用记录。第一个场景上线后按实际调用量决定。单次最大 token 由场景任务卡规定。

### S-06 · 供应商适配层

第一版可以只支持 OpenAI-compatible API key，但代码结构把它视为第一种 adapter，而不是把业务层写死为某个供应商协议。

**解决的问题**：未来增加其他协议或自定义网关时，只替换适配层，不重写 slug、摘要、翻译等业务功能。

## 6. 第一阶段范围（v2，D-182）：接入层最小子集 + 语义 slug 候选

本节是候选范围和拟验收条件，**不能替代 D-090 要求的 slug 任务卡**。实施前须另写任务卡，补齐默认模型、总时限、单次最大 token、工具与权限、人工确认和自动保存规则。

**场景：语义 slug 候选**（沿用 D-181）

- 输入（D-185）：当前语言的标题与摘要，不发送正文；只在 Kai Li 点击按钮时调用，摘要为空时按钮不可用。数据类别为 `draft`（首次发布前生成），因此只能使用允许 `draft` 的连接。
- 输出：结构化的候选 slug 列表。
- 能力：`structured-output`（隐含 `chat`，见 3.4）；第一阶段唯一的默认模型就是 `structured-output` 的默认模型。
- AI 只生成候选；本地规则检查 ASCII、小写、长度、保留词和唯一性，不合格的候选丢弃。
- 不覆盖用户输入；不阻塞保存或发布；首次发布后不再生成。
- 失败时提示原因，用户直接手填 slug。

选择理由：输出最短、可用 D-181 的本地规则机械验证、失败时用户手填即可，适合验证接入层。

**接入层第一阶段只实现场景用得到的部分：**

1. 连接配置：baseURL、API key（按 S-01 选定方案）、启用、优先级、allowed data classes；
2. 连接测试；
3. 模型查询与手动添加模型；
4. 能力标签（`chat`、`structured-output`）；
5. 一个能力默认模型；
6. 按优先级依次尝试、总时限、错误分类（3.2）；
7. S-02 的最低限制；
8. 调用记录（S-05）；
9. 后台显示每个连接最近一次测试 / 调用结果。

**拟验收**：以下情况行为符合 3.2、3.5、S-02、S-03、S-04 和 D-181：

- 正常返回候选；
- 主连接失败，切到备用连接；
- 没有允许 `draft` 的连接，直接失败；
- 显式指定的模型所属连接不允许 `draft`，返回配置错误且不发出请求；
- 全部连接失败；
- API key 无效、模型不存在、收到重定向；
- 返回格式错误，不切换、不重试；
- 所有候选均未通过本地 slug 校验；
- 已填写的 slug 不被覆盖；
- 任一语言首次发布后不再生成。

暂不纳入第一阶段：

- 文章摘要按钮；
- 英文翻译；
- 文章编辑器 Chat；
- Resource / Idea 研究；
- 向量检索；
- 公开个人 Chat；
- MCP 工具；
- 冷却状态、预算、embedding / vision 能力及其默认模型。
