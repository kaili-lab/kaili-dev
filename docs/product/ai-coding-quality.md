# AI coding 质量约束：概念、项目现状与逐步实施

记录日期：2026-10-27。用途：先理解质量保障由什么组成，再按项目风险逐步实施，减少重复性的人工代码审查。

**状态：方法与候选实施路线；本轮只写文档。** 本文不新增强制门禁、不修改 CI、不批准安装、迁移、发布或基准更新。现行要求仍以 [实施计划](implementation-plan.md)、[决策日志](decisions.md) 和工程配置为准。模型复核提高了方案被质疑的程度，不等于已经证明实现安全，也不构成行业统一标准。

## 1. 先理解我们要保证什么

代码质量包含功能是否符合需求、数据和权限边界是否可靠、代码是否便于继续修改，以及变更能否安全交付和恢复。自动化检查只能检查已经表达出来的规则和场景；AI 同时写实现与测试时，二者可能共享同一个错误理解。

以「AI 修改文章保存功能」为例：保存成功只是其中一个结果，还需要证明公开页没有变化、另一语言没有被覆盖、无权限请求不能写入、失败时没有留下半份数据。这些成功与失败判据先来自需求，不从当前实现反推。

目标是让机器重复验证明确规则，让独立审查聚焦规则未覆盖的设计与遗漏。人仍负责需求含义、重要验收规则、风险接受、视觉基准批准，以及需要授权的迁移和发布。已确认的规则可以复用，不要求每个小改动都重新人工审批。

## 2. 六个组成部分，各自能证明什么

以下 A–F 是本次讨论采用的工程框架，不是六个必须串行执行的阶段。安全、隐私、可维护性和依赖风险贯穿各项，不另造一个孤立的「安全阶段」。

| 部分 | 做什么、为什么需要 | 能发现的失败 | 单靠它不能证明什么 |
|---|---|---|---|
| A. 需求与验收 | 把期望变成有输入、结果和边界的例子，给实现和审查共同依据。 | 保存草稿却改变公开文章，违反事先约定。 | 规则完整、实现一定符合规则；验收依据本身也要接受质疑。 |
| B. 实现约束 | 用类型、lint、模块边界和固定检查约束已知错误，减少反复人工指出同类问题。 | 页面直接导入数据层、非法颜色或明显类型不匹配。 | 未编码的设计问题、重复抽象或业务理解错误。 |
| C. 行为验证 | 在合适层级观察结果：纯函数规则、数据库约束、HTTP 与浏览器流程。 | 保存后刷新丢失、事务失败留下部分写入、匿名读到私有图片。 | 未覆盖的输入、运行环境和并发条件都正确。 |
| D. 独立审查 | 对照需求、差异与证据寻找实现和测试的共同盲点，也检查维护成本。 | 实现和测试一起忽略撤下文章后的匿名媒体访问。 | 模型的一次「通过」等于无缺陷；审查发现必须有依据并复核。 |
| E. 交付控制 | 把检查结果绑定具体代码版本和构建产物，并按实际交付路径执行。 | 测试跑的是旧版本、缺少某项检查却继续部署。 | CI 绿灯自动等于需求正确；管理员仍可能绕过远端规则。 |
| F. 运行反馈与恢复 | 部署后验证、观察错误、演练恢复，把生产发现转成回归场景。 | 只有真实 binding、回调或数据库状态下才发生的故障。 | 在事故前发现所有问题，或只有告警没有恢复步骤也足够。 |

各部分的依赖很具体：D 需要 A 的依据，E 要确认 C 的证据属于待发布版本，F 发现的新失败要反馈给 A/C。不要用测试数量、覆盖率或模型评分代替这条因果关系。

贯穿约束：

- **独立验收依据：**先有场景和关键不变式，再写实现；测试预期不能只是复制当前函数输出。高风险规则在实现前确认，低风险已定规则复用。
- **输入和权限边界：**AI 只拿完成任务所需内容。私有正文、Idea、`.dev.vars`、token 和会话数据不进入模型输入或测试报告；`.gitignore` 不能阻止工具误读这些文件。
- **小范围改动与恢复：**优先让一份差异只改变一个可解释行为；越容易说明影响范围，越容易审查、验证和回退。数据库变化另查新旧代码兼容性，不能假定回滚 Worker 就回滚了数据。
- **依赖风险：**锁文件保证版本可复现，不能证明依赖安全；依赖变动和定期审计需要考虑已知漏洞、实际使用路径及上游修复。

## 3. 学习与讨论顺序

先定一个问题和贯穿例子，建立 A–F 小地图，用一至三个新失败检验理解，再按需要粗看项目的「有 / 部分有 / 没有 / 未知」。选择深入方向时同时说明兴趣、前置知识和风险；深入后才给具体实施项和验收方式。

例如可先讨论「为什么测试全绿，草稿仍可能泄漏」，再深入验收依据或权限行为；不用第一轮就列出所有 CI 工具和脚本。纯概念讨论可以停在地图与例子，紧急故障则直接追失败路径。

通用讨论方法已另写入用户指定的 `personal/docs/deep-dive/模块学习元方法.md` 的「陌生主题定向：从概念地图接入六步」章节。该文件属于个人知识目录，本文不要求 CI 访问它。

## 5. 将来逐步实施：先保障交付，再扩大覆盖

以下是候选顺序，**所有条目都还不是本轮已实施的成果**。接手时先检查是否已由别的任务完成；只有剩余缺口进入实施。每次选一项，先定义可观察的失败与通过条件，再决定工具和脚本，不先建通用检查平台。

### 第一批：让已有证据可复现，并沿实际交付路径执行

| 候选项 | 何时做、解决什么 | 最小验收与边界 |
|---|---|---|
| 明确 PR 或直接推 main 的检查入口 | 下次调整自动交付时；仅加 PR workflow 对直接推 main 无效。 | 若采用 PR：检查绑定候选提交，合并受必需状态检查约束；若直接推 main：关键检查成为远端迁移和部署的前置。核对远端规则与可绕过权限，不把有 CI 文件等同强制门禁。 |
| 干净环境验证和可追溯报告 | 接入浏览器门禁前；解决依赖本机状态和证据找不到。 | 固定 Node/pnpm/浏览器环境，用合成数据和隔离本地 D1/R2，在干净环境运行适用 check/build/dry-run/e2e。报告记代码 SHA、命令、环境、退出码、未执行项；CI 保存失败 trace/截图与日志，说明保留期和访问权限。报告脱敏，不记录 Cookie、请求凭据或真实正文。 |
| 视觉基准的保存和更新 | 将视觉回归接入 CI 前。 | 从仓库或有版本、受控的制品存储取得已批准基准；固定系统/字体/浏览器，基准缺失应失败。明确批准者和更新原因，不能自动用当前截图消除差异；若迁移平台导致像素差异，重新审阅候选图。私有笔记和真实内容截图不整体入库。 |
| secret 与敏感文件检测 | 下一次提交检查增强时，与交付能力建设同批考虑。 | 暂存内容和 CI 候选变更分别检测，故意违规合成样例失败、合法样例通过；仅报告文件、位置和规则，不输出密钥。按需对 Git 历史做本地扫描以发现早期泄漏；实际泄漏要撤销/轮换，删掉当前值不够。模型不读取真实配置，CI 无需生产密钥运行普通验证。 |

### 第二批：优先降低迁移与发布失败的代价

| 候选项 | 何时做、解决什么 | 最小验收与边界 |
|---|---|---|
| 迁移自动发现与 schema 一致性 | 下次 schema 或迁移变化时；沿用现有保数据测试。 | 新增迁移无需手工登记也能进入空库与旧库升级验证；缺迁移、外键损坏或子记录丢失能失败。schema 比较覆盖列、约束和必要索引；手写 trigger 独立验证，不能用「generate 无变化」代表完整一致。迁移生成检查在临时副本执行。 |
| 迁移兼容与恢复演练 | 下一次有数据结构风险的发布前。 | 验证「迁移成功但部署失败」时旧 Worker 是否仍可运行；明确恢复工具、可恢复时间范围、数据损失边界和操作者，在合成环境实际恢复并检查数据。优先选择新旧代码都兼容的迁移，破坏性变化单独评审授权。 |
| 生产构建上的后台关键路径 | 数据访问/鉴权变化或正式域名切换前。 | 在隔离环境用生产构建和受控合成会话跑保存→发布→公开读取→撤下，并验证匿名和过期会话拒绝。测试便利入口不能进入生产包；真实 GitHub 回调另做授权的环境验收，不让每次 CI 依赖个人账号扫码或真实内容。 |
| 部署后验证与停止/恢复条件 | 下一次获授权部署时。 | 验证已部署版本、公开页/SEO/静态分享图、匿名后台与媒体边界、必要 binding；失败有明确停止和恢复步骤。线上写入验证需专用合成内容和授权，不自动向生产灌 seed；本地通过不冒充线上验证。 |

### 第三批：补明确的行为缺口，不重复堆测试

| 候选项 | 触发与验收方向 |
|---|---|
| 开发专用路由覆盖 | 新增测试/设计工具路由时，明确哪些只能开发使用；证明生产构建不可达且无副作用。覆盖来源要能发现新增文件，不能让生成器与测试共用一张遗漏清单后互相证明。按用途分类，不按 `admin` 或下划线一刀切。 |
| 私有数据不进客户端 | 修改服务端/客户端分层或序列化时，用合成私密标记检查客户端产物和公开响应；不拿真实 secret 当扫描样本。HTTP 404 只证明入口不可达，不能证明包中没有私有内容。 |
| 鉴权实际入口的失败行为 | 先复用已有匿名上传、退出同源、session 摘要和会话失效测试，再补未覆盖的 OAuth 回调失败、过期/重放和敏感 RPC 边界。调用实际处理路径并观察拒绝写入、cookie/会话状态；不只检查常量或 helper 返回值，不为测试先重构一层纯函数。 |
| 浏览器错误统一监听 | 在已有 e2e 上收集 pageerror、相关 console error、必要同源子资源失败；故意 404、请求取消和错误态用例局部声明预期。未知错误失败，不能靠全局白名单或重试掩盖。 |

### 第四批：按发生频率和维护收益补充

- **键盘与焦点：**表单或弹窗修改时验证键盘可达、焦点可见、关闭后的焦点恢复；静态 JSX 无障碍规则不能代替交互检查。
- **性能预算：**资源加载和依赖变化时复测现有慢速 3G 标准；分别记录浏览器 JS/CSS/图片和 Worker 包体，不把 Worker gzip 总量当浏览器 JS。阈值基于新的实测基线与用户体验，不直接套旧 OG 的数字或任意增长百分比。
- **依赖审计：**依赖变动或定期检查已知漏洞，评估是否涉及生产路径及修复可行性；扫描服务不可用记为未完成，不能报告无漏洞。不自动执行破坏性升级。
- **轻量文档检查：**确有引用漂移时检查相对链接、决策编号和 supersedes 目标；允许明确标注的本地/历史证据，不强制每个旧进度行都变成统一格式，也不校验文档中的测试数量。

## 6. 执行层级与人工审查边界

这里的层级是候选组织方式；当前没有 `verify:commit` / `verify:pr` / `verify:release` 聚合命令，不应直接复制这些名字执行。是否新增命令取决于现有命令是否已足够清楚。

| 时机 | 检查职责 | 证据要求 |
|---|---|---|
| 开发迭代 | 与改动直接相关的类型、lint 和行为检查；不要求每保存一个文件就跑全套。 | 失败可定位到输入、规则和观察结果。 |
| 本地提交 | 沿用 `pnpm check`；按计划加入必要的暂存内容检查。 | 非零退出阻止普通提交；承认可绕过，不代替远端执行。 |
| 合并或部署前 | 根据实际 PR/main 路径执行适用 build/dry-run/行为/视觉/迁移检查。 | 绑定候选提交和产物，记录未执行项；生产凭据只给需要它的部署步骤。 |
| 发布与发布后 | 环境差异、迁移兼容、恢复与线上验证。 | 发布版本、结果与恢复路径可追溯；外部副作用遵循明确授权。 |
| 独立复核 | 贯穿方案和完成验收后的关键节点，针对需求、改动和证据找遗漏。 | 问题含依据、影响与修正方向；整改后验证受影响路径，并复核。保持现行项目要求。 |

高风险的权限、数据迁移、不可逆删除、新公开边界和验收规则变更，值得集中人工或独立审查；重复的类型错误、格式、已编码规则交给工具。不能用一个预设的「减少人工 review 百分比」证明流程有效。

评价新增检查时看三个结果：是否抓住了有意义的错误、误报和偶发失败是否可控、日常维护与等待是否值得。反复需要人工解释但很少发现真实问题的检查，应调整范围或撤掉。

## 7. 暂不采用的做法与此前结论修正

- 不用全局覆盖率百分比代替业务边界；覆盖率可以帮助定位未执行代码，不能独立证明质量。
- 不把变异测试全面铺开，也不声称「穷举就没有价值」；关键断言仍可能写错，有具体疑点时可定向验证。
- 不在每次提交运行全量浏览器、视觉和限速测试，也不为每个低风险改动增加多模型全仓复核；保持适用验收和现有独立复核要求。
- 不把自写几条 secret 正则当完整防线。实施时比较成熟工具与项目维护成本；需要安装时按授权规则处理，不能因本轮不安装就永久排除工具。
- 不把 AI 结论当作稳定的自动放行分数，不通过更新测试预期、扩大白名单或重生视觉基准掩盖回归。
- 不断言「有 CI 就无法绕过」。CI 执行、必需状态检查、分支保护与管理权限共同决定执行力度；本轮未查询远端策略。
